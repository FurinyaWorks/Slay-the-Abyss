# 原生轻量 2D：启动→选角→战斗完整竖切实验

> 2026-11-08 / **Owner 授权的定向技术实验** / Draft 方案，不是正式迁移、设备验收或发布通过。
>
> 目标：在**保留 Run/Combat/Lua 核心**的前提下，证明能否用千星原生 2D 控件、低部件数角色、控件复用和 Tween，实现用户认可的高品质、流畅的完整游玩路径。先验证再定夺，不因社区示例存在就宣称问题已解决。

## 一、路线与非目标

- **优先路线**：已有 Lua 规则 + 原生 2D 卡牌、按钮、文本和背景 + 可复用的低部件数原创/合法角色视觉。
- **后备路线**：原生 3D 局部特效或场景，仅在同设备证据证明 2D 不满足目标时再讨论完整迁移；保留实验 PR [#553](https://github.com/FurinyaWorks/Slay-the-Abyss/pull/553) 及在途正式化 Draft [#556](https://github.com/FurinyaWorks/Slay-the-Abyss/pull/556)，**本 PR 不修改/合并/关闭二者**。
- **发行范围**仍是 [SCOPE](../../docs/SCOPE.md) 的岩系旅行者、第一和第二幕及自然结算；不开放雷电将军、不重做数值、不增加持久化，不恢复已禁用的逐卡精绘插画。
- **现有批准的 UI 参考**以 [2026-11-05 采用记录](../../docs/design/APPROVED_UI_ADOPTION_20261105.md) 为准。菜单已经好看的部分只做实证性能修复，禁止因新素材而擅自整体改版。
- 本 PR **只承载样本方法、实验合同和 Agent 接线说明**；真正运行时代码与候选应由 Agent 在独立实施分支交付，经过独立评审与正常准入后再合入。不得假称本 PR 已修复卡顿。

## 三、逐屏实现，拒绝无限扩张研究

1. **冻结基线与定位首个卡点**：使用相同 develop 源码身份，盘点开屏/菜单、背景初始化、选角、战斗各段 Lua 初始化、UI 创建、图片/模型资源分配、首次可交互时间。先复现具体慢点，再定点调整。独立候选依次隔离 menuBackground/selectionAvatar/battlePortrait，cards 始终 false；不同时改玩法或主题。
2. **菜单/按钮**：保留批准构图及返回/结算行为；以合法原生图片 ID、分层底板、四态预设按钮和少量 Tween 制作一套统一样式。仅替换最不满意的一个按钮作 A/B，测试鼠标 hover/down/up、手机触屏、手柄聚焦、退出与重进。优先利用同一模板和共享主题，不复制 35 套不必要控件。
3. **选角/角色**：先做原生 UI 低部件数角色（约 30–60 控件/角色作为研究起点，**不是官方性能安全线**）和原有职业数据显示；停用或惰性加载高成本重绘路径。动作以父级变换/有限帧组切换为主，不采用对数百像素每块独立建立 Tween 的方案。
4. **2D 背景**：优先原生图库/可验证官方背景、少数可复用分层图块和缓存；比较当前加载与轻量版的视觉/启动成本。不能因小魔女/蒙德案例外观漂亮就把上千场景物件整包作为背景，也不能假设支持任意 PNG 战斗贴图。
5. **完整首战**：真实 Run/Combat 驱动岩系旅行者与 2–3 名真实首幕敌人；同一卡组在 1/5/10 手牌下抽牌、点选、拖动、选敌、出牌、敌方回合、受击、死亡、奖励、回图；至少覆盖玩家/敌人待机→攻击→受击→死亡。坚持唯一伤害/结算来源、输入互斥和有限容量缓存。
6. **自然游玩闭环**：从启动→菜单→选角→首战→地图→商店/事件/精英/Boss→第一幕→第二幕→结算，保留每个页面最后认可的文案、布局与触屏语义。工程切片可分步提交，最终交付**一份完整可玩的 2D GIL**，不只交局部演示页。

## 四、A/B 方法：两层实验，不能作弊

- **同一试玩 GIL 中**允许便捷切换旧/新皮肤或演出方案供用户直接比较；但是 A/B 的资源、模板、动画不应在另一方案中后台运行。每次切换先清理与核对 live 控件/实例归零，再进入候选。
- **冷启动和真实资源占用**须以同一核心代码生成的两份**分别打包**的基线/候选进行受控对照；同时打包两套美术会污染首载、包体与内存结论。记录两份 GIL 和所有标志的 SHA256，程序化导入可减少用户手工多次操作。
- 固定测试机、分辨率、游戏版本、RNG 种子、战斗命令、卡牌数量、输入序列、相机/背景、热/冷启动定义。记录重复次数并交替 AB/BA；失配样本明确作废，不用不同画质/场景给“加速倍数”。
- 指标：冷启动到首屏可操作、角色初次显示、首次开战、开背包/返回、抽出牌响应、端到端帧时间 P50/P95/P99 和超过 100ms 的长帧数量、脚本回调间隔（单独列）、真实控件/场景实例高水位、分阶段创建/销毁、峰值内存与 20 次重进/切场后的残留、官方平台容量。
- **官方 PC + 实体 Android** 必须分别取证；Node/Fengari、模拟器 PNG 和 OnUpdate 间隔不代替 GPU/实际屏幕 FPS。手机建议验证持续约 30FPS、P95 帧时不高于 33.3ms 的研究目标，60FPS 理想；这些是**目标而非现有成绩或引擎承诺**。
- 人工目视验收：相同内容截图/短录屏并排确认角色辨识、屏幕统一性、文字清晰、按钮状态、拖牌触感。漂亮但导致不可接受帧时，和快但角色不可辨认，均不算通过。

## 五、验收/No-Go 与保底

**2D Go**：真实 GIL 从菜单到两幕结算可玩；玩家认可画面；真实 Android 达到本轮约定的流畅体验指标；连续操作、20 次重复出入无无界增长；规则与输入不回退；素材权利明确。符合后再向 Owner 建议终止完整 3D 迁移。

**2D 不通过**：保留具体失败画面、阶段、数字和候选 SHA，优先判定是美术图元、UI 更新、动画、加载、模型还是客户端基础瓶颈；仅在验证无法以轻量 2D 达标时，提交 3D 成本对照，不自动全面迁移。

**缺实机窗口**：完成离线候选、脚本测试、GIL 写入读回与可交付说明，显式记官方导入/PC/Android 为 UNVERIFIED，不说“工业品质已达成”。
