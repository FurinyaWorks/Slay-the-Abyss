## 第一件必须做的事：找出“到底为什么卡”

优先分析真实 candidate 的 art flags、背景加载、选角显示、战斗单位资源生命周期和原生 UI 构建，不再泛泛提出“容器”“缓存”“事件驱动”这种项目已经部分做过的建议。

- 使用相同源码/seed/候选装配流程对照 **当前启用的背景、选角、战斗肖像** 与逐项关闭/低负载替代。卡牌逐张精绘 art-cards 保持 false。
- 冷启动与热切换分开；记录首次可点击菜单、首次选角角色可见、首战 ready、卡牌首次可操作、关闭/重进、内存和控件峰值。检查艺术加载是否先于交互、是否按帧创建、是否重复销毁重建、是否出现长期大量隐藏常驻实例。
- 采用真实日志与可复现 RED 找到瓶颈，**一次只改一个受测因素**。已存在的同值 setter 缓存和事件驱动机制只需复用，不再重新发明。

## 第一版具体要交付的画面

- **菜单/按钮**：保留已经批准的构图；仅针对难看的部分，借鉴“果冻感 UI”“好看的 UI”“受龙所选”的分层、色彩、原生四态和有限 Tween。先做一个真实可点击按钮，看 normal/hover/pressed/disabled 与手机效果。若重塑后不比现有版好，就保留原版。
- **选角**：岩系旅行者优先。研究低负载 UI 角色模板与像素小人，自己构建或合法复用一套清晰的人物表现，目标是尽量少控件、冷载短、切换不卡。角色名称、牌组信息、选中/返回真实有效。
- **背景**：优先官方现成图片、低层数构图与缓存；保留原有高品质画面中视觉表现好的部分。别把“蒙德城”等几千对象场景当成无成本的 2D 背景；不假定 PNG 任意上传能力。
- **战斗角色**：至少我方+2至3敌人，全套待机/攻击/受击/死亡，优先父容器动作与低开销帧组/状态切换；参考动态可莉/派蒙的动作图，但辨别“原生场景元件”与“客户端 UI”，不每像素建立数百 Tween。
- **手牌**：保留现有卡牌框、剑/盾/能力图标、文字、10 手牌及鼠标/手机安全交互。对照现有 lerpSnap 与原生 Tween 时固定同曲线同时间；将取消、归位、拖动中断与唯一动画写入者作为硬要求，不得误触发重复出牌。
- **全流程**：直接接真实两幕 Run/Combat 与 UI，不仅 seed=42 假战斗或测试按钮。保留奖励、商店、事件、地图、跨幕、失败/胜利、返回与重开；不因演出失败重复执行伤害/领奖。

## 怎么验证，而不是写漂亮报告

1. **构建**：独立 2D GIL + 不可变候选 ID、源 SHA、最终 GIL SHA256、各 art flags、模板/模型清单及完整 GIL 读回。
2. **离线**：先跑最小相关测试、UI 生命周期与输入合同、正常战斗事件与回滚、关闭后的释放；再按风险跑现有 CI，不为了让数字好看删断言或降低门禁。
3. **真实体验**：同一候选在官方 PC 与真实 Android 端记录启动/选角/首战、1/5/10 手牌、敌方攻击、两幕流程。若拿不到桌面操作窗口，先完成离线 GIL 且将 PC/Android 明确记为未测，**不主动抢用户键鼠**。
4. **性能对照**：同种子/操作、固定截图质量与设备，记录首屏可操作耗时、帧时 P50/P95/P99、100ms 以上长帧次数、交互响应、峰值内存/控件与场景实例、20 次切换残留、官方容量。**OnUpdate 不等于真实 FPS**；同时装载两套皮肤不能拿来比较冷启动。
5. **审美验收**：给出用户可以直接看的逐屏对比截图和短视频：主菜单、选角、初战、10 卡、敌方行动、战后奖励、地图、商店、第二幕与结算。整套色彩、字号、动效与角色风格一致，不机械照搬第三方版权素材。
