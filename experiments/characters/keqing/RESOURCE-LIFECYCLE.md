# Candidate resource lifecycle module (not wired)

`resource-lifecycle.lua` is a pure reducer with no dependency on Combat, Actor, queues or UI. It prepares the minimum character-owned boundary for shared integration: attack snapshot, successful paid-card resource transition, and a queued owner-end cleanup action. Constants are supplied from the candidate single source (statusRules and starterRelic in the test), not treated as official game values.

A setup event emits a one-shot fixed-block intent when the candidate relic is enabled. The module does NOT execute that intent; it must be enqueued at the actual setup point by the eventual owner of the transaction, with rollback covering resources and the intent together. It cannot be called simply after an arbitrary effect queue if an earlier setup has already generated reactions or death. `resolved` is an exactly-once dispatch contract, not an idempotent replay endpoint, and does not itself validate payment. Its present scope is the simple starter, not cards with multiple resource events in one play.

Existing lifecycle inspection: `abyss_combat.lua` has `prepareExperimentalPlayerEnd → ordinaryOwnerEnd`, routed through `abyss_end_turn_powers.prepare/apply` and `abyss_power_schedule.ownerEnd`. EndTurn itself can pause for retained cards or other pending choices. Therefore resource cleanup belongs to an explicit queued owner-end action, not to the public endTurn request entry. No public arbitrary callback registration exists. Ordering relative to other characters' owner-end resources must be coordinated, including Ganyu's leftover-energy conversion before discard/ice-rain. Shared Combat/Actor files remain untouched.

The pure Lua test covers setup/recast/detonate, attack-card charge vs skill, first-setup relic intent, repeated setup after recast, next-owner-end expiry and input/result isolation, with malformed primitive state rejected. This does not verify queue resume, save schema, formal UI, reaction ordering, relic execution or formal registration. All source/human/balance gates remain HOLD. Next integration must reuse the shared queue's transaction and continuation, rather than replaying actions or registering a parallel callback system.
