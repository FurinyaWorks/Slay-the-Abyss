# 更新日志与版本记录写作规范

> **直接采用行业规范，不再自创：** [Keep a Changelog 1.1.0](https://keepachangelog.com/zh-CN/1.1.0/)（面向人的更新日志）和 [Semantic Versioning 2.0.0](https://semver.org/lang/zh-CN/)（版本号）。参照已有的 [CHANGELOG.md](../../CHANGELOG.md)。

## 四类记录，各管各的

| 位置 | 负责内容 | 禁止混入 |
| --- | --- | --- |
| `CHANGELOG.md` | 玩家能看到或操作到的新增、变更、修复；按版本倒序，每条一句 | PR/CI、开发代号、代码重构、试验结果、未合入功能 |
| [版本索引](README.md) / [路线图](ROADMAP.md) | 版本号、Tag、对应 Commit、源码阶段与官方发布状态、下一步范围 | 冗长的玩家版本文案 |
| [工程记录](ENGINEERING.md) | 架构、性能、构建、测试及证据细节 | 重复发布公告 |
| `data/release/publications.json` | **平台成功发布**的作品身份与回执 | 代码合并、打 Tag 或未经证实的发布日期 |

## 固定步骤

1. **以已合并的实际行为为准。** 从前一个版本到当前提交核对变更，判断玩家是否真的可以使用；在途 PR 和实验资产只写路线图，不冒充已开放。
2. **先写 `## [Unreleased]`。** 用 `### 新增`、`### 变更`、`### 修复` 中真正需要的分组，每条是“具体位置 + 实际变化 + 玩家收益/问题”。不复制自动生成的 Git Commit 标题。
3. **确定发布批次后才归档。** 按 SemVer 选择 `PATCH`、`MINOR` 或 `MAJOR`，将已核实的 `Unreleased` 项移到 `## [X.Y.Z] - YYYY-MM-DD`，在顶部保留新的 `Unreleased`。
4. **同步代码版本。** 同一个变更必须更新 `package.json.version`、`package-lock.json.version`、`package-lock.json.packages[""].version`、`.release-please-manifest.json["."]`，并保证 CHANGELOG 有该版本段落。旧 Git 提交不重写；当前代码的错误版本字段必须及时纠正。
5. **强制检查。** `npm run check:release-notes` 已加入 `npm run check:rules`，检查三个文件一致、更新日志格式、版本顺序与玩家可读性，失败不能合并。发布前仍运行原有 Full 与实际平台/手机验收，不因日志检查成功就表示可发布。
6. **Tag 不等于平台上线。** 历史 Tag 按真实旧提交回溯，写明其源码检查点性质，绝不强制移动。只有真实平台成功后才能补写发布回执。

## 好与坏的对照

| 不推荐 | 推荐 |
| --- | --- |
| “V25 战斗 UI 迁移、修复 #634、质量棘轮通过” | “重新安排战斗画面的手牌、能量和敌人信息，让重要内容更容易看清。” |
| “优化了很多操作体验” | “修复手机选牌时目标提示与能量信息显示异常的问题。” |
| “集成角色原生资源与 UI 生命周期” | “更新旅行者的待机形象，使角色展示更自然。” |
| “新增胡桃、开放第三幕”（仅在实验分支存在） | 尚未面向玩家开放：保留在路线图，不写入玩家更新日志 |

用克制、具体、可验证的短句；不写“史诗级”“彻底不卡”“大幅提升”这类未经数据或实机验证的宣传语。

## 本次版本例外的收口

- 2026 年 11 月的 **1.1.0** 与 **1.2.0** 是回溯标记的源码阶段，而不是宣称玩家曾收到对应的千星正式更新；旧提交中的 `1.0.0` 不重写。
- **当前 `develop` 仍为 `1.0.0`；待合并的 #665 将已合入部分的版本元数据补正为 `1.2.0`**，包括 package、lockfile 和 release manifest；只有本轮大改实际合入并形成可验发行版本时，再统一升到 `2.0.0`。
- 2.0 更新说明只公布这次真正上线的页面与操作；新增页面非关键音效留作下个 `2.0.1` 修补，不在 2.0 里提前宣称新增。
