# TASK-104：产品结果闭环——基于已验证事实的根因论证与验收合同

> 2026-11-09，Owner 授权登记本任务并提 PR，交现有 Agent 实施。本文件是实施参考与证据边界，**不是**已完成的修复、已证明的五层因果或设备性能通过报告。

## 1. 先确定问题的层次

**产品目的**：利用千星奇域的发行/玩家入口，在其平台约束内交付一款玩家愿意游玩的两幕卡牌肉鸽，达到 Owner 已批准的 V25 视觉和交互体验。

**玩家可观察到的问题**：此前高成本美术会在进入菜单、选角或战斗时迟到、逐块出现；同一时段还有输入卡顿、长时间等待以及视觉设计未完整还原等反馈。不要将“页面完整呈现时间”“持续帧率”“首次启动成本”“官方容量”混成一个性能数字。

**治理问题**：大量工程工作改善了 SCC/CC、依赖和 CI，也减少过无效 setter，但没有让这一组玩家症状成为自动复现、可反证、可追踪到发布的验收主线。

## 3. 实施与反证的原则（保留 Agent 技术自主权）

**先以症状建可重复场景**：固定用户操作、同一源码/种子/界面状态和合法内容，显式记录界面完整可见的定义、完成时间与创建时间线。保留失败基线，不用静态文件读回、脚本 ready 或单次 SetVisible 代替“玩家完整看到并能操作”。

**每次实验区分两种因果**：“怎么创建”（零件级/完整原件组件）和“什么时候创建”（按需/提前）。尽可能通过同画质同负载的正交对照；做不到时写明不可控变量，不以不同画质两候选的速度直接作路线判定。持续 FPS、CPU/SDK step、官方容量与构建文件大小必须分别测量。

**模拟器优先但有边界**：绝大多数 Lua 调用、模板层级、资源分配、取消/重入/泄漏、业务交互和部分 SDK 计算成本可低成本回归；它无法可靠模拟真实 GPU、帧呈现、手机发热降频或官方上传容量。先让模拟器中的已知问题全部暴露并被修复，再用有限实机窗口做关键同候选校准。未校准前不得宣称“模拟器能预测真机大部分 FPS”。

**验收必须分层**：代码/模拟器证明、实际 GIL 写入读回、官方导入/ready/容量、PC/手机体验与 V25 视觉确认分别记状态。低成本证明能够阻断已知失败，却不能将缺失的高成本验收自动打成 PASS。无需为每个普通 PR 都强制手机验收。

**自动纠偏**：连续两次针对同一假设的合理受控实验没有改善原始症状，应停止沿同假设继续堆补丁并重新定位；多次修复失败则审查架构与基线是否错误。允许继续推进独立有效任务，不因一项不可实测阻塞所有 Agent。按实际证据调整优先级，而不是按 PR 数量或提交量评价进展。

## 4. V25 视觉不可让步

- **最终外观以真实冻结的 V25 批准原型、状态和截图为准**；原件若仅在 Owner 私有工作树，核实来源和具体缺口，不凭空宣称已获得全部资产。
- 社区 GIA/GIL 的作用是提供成熟的技术路径、控件模板、交互与渲染能力；可以适配，但不能把它们的直接外观当正式卡框、按钮、人物、背景。不能重新做成原版《杀戮尖塔》UI。
- 视觉质量、交互清晰度、合法 10 手牌、实际敌人数、两幕 Lua 规则不可通过偷偷删减以换取速度。无法保真的地方要可见地留缺口，待 Owner 决策。
- V25 原生实施归 TASK-103 / PR #565，本任务只补“是否真正交付产品效果”的可执行验证与长期机制，避免争抢文件和重复任务。

## 5. 这次机制是否真正成功的判断

让实施 Agent 用 PR #565 的真实变更演示：一项“控件新增降为0 / 选角 step 加快但启动变慢”的结果，自动得到**部分改善、仍未产品验收**；缺证据/伪造同源/假 ready 的负控会被既有检查正确拒绝；输入与 V25 视觉不被错误替换；在不增加每 PR 重型运行的情况下，能定位下一项有效工作并保留无法实机确认的缺口。

这比“新增一份 Harness 规范”更重要。文件本身不会自动改变 Agent 行为；完成须有实际测试入口、失败样本、可复核修复结果及正确的 Backlog/PR 收口。

## 6. 可执行入口与任务收口

2026-11-09 接手 #581 后实现以下机制。原文中的“待实施”描述保留为登记时的历史；本节记录实际机制和本轮边界。

- `npm run replay:outcome -- --receipt <adapter-receipt.json> --sdk <actual-runtime.mjs> --out <新的report.json>`：复用 #565 已有 actual-GIL 投影和固定身份 BeyondSimulator 0.5.2 的 `Gr/vi/dn`，不加载 renderer，不启动官方客户端。默认菜单→选角→取消返回20次；只调用原指针接口，不点确认、不创建 Run。小诊断可用 `--cycles 1 --frame-limit 2`，其输出不能通过完整合同。
- `npm run verify:outcome -- docs/evidence/product-outcomes/TASK-104.json`：验证绑定文件的实际 SHA256、完整事件与页/输入/资源关联，重新推导诊断。退出0只表示证据足以作诊断；`productStatus` 和六个官方/设备/视觉层始终是 UNVERIFIED。
- 加 `--require-offline-pass` 才要求离线体验关口 PASS。固定合同是20次完整往返、实际输入命中、页面模型完整、暖重入对象不增长、非初始化 SDK 同步操作不超过100ms。100ms是诊断阻塞预算，输入操作含 move/down/两次step/up，不是单帧GPU预算；初始化长阻塞单列。证据不能自增预算，正常无阻塞模型正例可过，缺证据/异常/错误摘要非零。
- 普通 Quality 在原 `tests/runtime-path-baseline.test.mjs` 入口运行轻量合同和负控，使用 `tests/helpers/product-outcome-contract.mjs`；不在每个PR运行SDK。`test:related` 继续按真实模块依赖选择。完整测试文件库存、分片、预算、原断言和 Fast/Full/队列规则保持。

回放先逐一核对实际 GIL、投影 save、exact Lua inventory 与原 mountedValues；SDK仅接受已记录的 `a62bb31a…` 导出摘要。追加export的临时副本位于新输出旁，原SDK、GIL及Lua不改写，结束重新核对身份。页面检查从候选静态树取得预期host全集，对实际组件有序完整子树及必要可见性做核对，并检查菜单/选角关键文字和可交互hit。删除整个host、隐藏必需host、截断子树、仅打印脚本ready均不能当页面完整。**这仍仅证明SDK模型结构，不证明像素已呈现或V25保真。** Node RSS/heap是进程观测，不是设备内存。

重大体验阻塞先复现再修复；已有产品任务/PR保持单一归口。若需要关闭“诊断机制”任务，使用 `product-diagnosis` 标签，并在 `config/product-outcomes.json` 固定登记 taskId、diagnosis 类型和已有产品PR归口，documentation链接同名诊断JSON。`verify:backlog`读取该记录：Done须包含真实回放、原症状失败复现、全部未验层负责人，且无未处理的实验复核/转向。去掉标签也不能让已登记任务逃逸。`product-acceptance`或未登记类型不能借用DIAGNOSED关闭产品任务；正式验收仍用既有 `verify:ui`、官方负载和同候选设备合同。

实验条目必须引用哈希绑定的baseline/candidate原始回放，指定原症状指标和可反证假设。判定器从回放计算before/after，以全部native树/资源、Lua工作负载、原生mount参数、SDK、观察器版本、环境和场景身份判定是否可比，忽略自报的 `controlled` / `before` / `after`。当前只允许固定 `abyss_component_bridge.lua` 作为单因素干预，单独记录intervention摘要；其他Lua变化默认不可比，后续须独审扩展合同。两次受控实验无改善输出 `REVISIT_HYPOTHESIS`；混入不同视觉/负载输出 `REVIEW_EXPERIMENT`，CLI非零并阻止Done。后续有效的重新测量可解除待复核状态，失败历史仍保留。摘要和哈希本身不自证执行真实性，独立评审仍须核对原始来源；没有新增签名、后台调度、并发锁或产品发布授权。

## 7. #565 本轮闭环实战

原始六实例历史SDK记录完整压缩保存在 `docs/evidence/product-outcomes/pr565-{old,new}-sdk.json.gz`，来自#565既有未改写的metrics-raw.json；两份原始JSON摘要分别为 `8abae690e1a51f731c9f515093848b16fb500b22a300ee4d0803a5ef942f90ee` 和诊断manifest绑定的新包记录。原旧新 GIL 分别是 `ae1dcf81…` / `207e4ad4…`。判定器直接从全部逐步数据计算nearest-rank中位数，得到初始化约1302.85→2452.27ms、菜单step约3.387→10.057ms、选角step约16.718→10.437ms，以及新版观测阶段零新增。自动输出 PARTIAL_IMPROVEMENT，标记startup/menu-step回退；不作异画质因果推断。

可比性producer只剥离server/client的 `meta.sourceFile` 和 `abyss_ui` 首行由构建器注入的精确UUID日志；其他Lua字节、native资源/元数据、serverLogic和mount参数全部参加指纹，原始候选/完整Lua/build身份仍单独绑定。producer源码摘要也绑定每份回放。用真实新候选的完整save在内存中只换目录与buildId，指纹保持一致；生产函数正负控另验证真正Lua、图元、规则或mount变化仍不可比，只有已登记bridge干预单列。这避免机制只能接受合成同hash对象而无法比较真实新构建。

既有安装器只下载一次，导致几秒的临时HTTP错误必须等整轮结束才可补跑。现只启用curl原生的2次重试、1秒间隔和60秒retry预算；单次max-time60秒、Node子进程总上限65000ms、固定Luacheck1.2.0/SHA256、缓存与下载哈希拒绝、所有CI作业预算和断言保持。没有新增外层重试器、下载镜像、CI作业、权限或依赖，也不对校验失败重试。

真实loopback HTTP+系统curl的RED复现两次504使旧安装器立即失败；GREEN验证504两次后200可恢复、持续504三次后非零、404不重试、坏缓存不发请求、下载坏哈希不写文件。测试运行原安装器的字节副本和独立临时配置，不复制实现；收在原runtime-path测试入口，原静态测试与测试文件库存不变。该suite本机约5.3秒，沿用现有未测文件10秒规划权重，不伪造Hosted测量。此修复仍须当前HEAD独审、正常Full及合并队列验证；原失败和取消历史保留。
